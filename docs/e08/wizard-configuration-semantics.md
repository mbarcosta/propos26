# E08 - Wizard Configuration Semantics

This document records the semantics observed in ADE, CIR, GMS and BPMN before changing the Automation Configuration Wizard UX.

## Guiding Rule

The wizard must translate business intent into technical configuration. `AutomationRequirement` remains an internal detection mechanism, but the user experience should start from the BPMN element intent and ask only for decisions that cannot be discovered, derived or generated.

## External Event And BPMN Message

An external event is an occurrence recognized by the infrastructure, currently by CIR after reading normalized messages from GMS. It is represented in CIR route configuration and may be delivered to Camunda as a variable.

A BPMN message is the model-level representation used by Camunda. It exists in the BPMN XML and is referenced by message start/catch event definitions. CIR sends its `messageName` to Camunda.

Existing behavior shows that an external event and a BPMN message often share the same name, but they are not the same object. The wizard should show this relationship, reuse BPMN messages already present in the model and hide the technical message expression/details unless needed.

## Start Message Event

For a message start event, the incoming message starts a new process instance. There is no previous instance to find, so the wizard must not ask how to correlate to an existing instance at this point.

The current code uses `correlationId`, not `requestId`. For START, CIR generates `correlationId` when missing and stores it as a process variable. The wizard should present it as an automatically created identifier available for future replies.

## Message Catch Event / Receive Task

For later waiting elements, an instance already exists. Correlation belongs here. The wizard should ask which available process datum allows CIR/Camunda to route the reply to the correct instance, normally `correlationId` produced at the start.

The GMS/CIR normalized email schema currently supports:

| --- | --- | --- | --- |
| `from` | String | `requesterEmail` | Sender. |
| `subject` | String | `subject` | Subject. |
| `body` | String | `body` | Text body. |
| `to` | Array<String> | `recipients` | Main recipients. |
| `cc` | Array<String> | `cc` | Copy recipients. |
| `messageId` | String | `messageId` | Message identifier from GMS/IMAP. |

| `advisorId` | Long | `advisorId` | Optional labeled value extracted by CIR if the incoming text already contains an ID. If absent, `ValidateAdvisorshipRequestWorker` can resolve the professor by name or email in PPG Management. |
| `studentEmail` | String | `studentEmail` | Labeled value extracted by CIR and used by the worker to search PPG Management. |
| `advisorEmail` | String | `advisorEmail` | Labeled value extracted by CIR and used by the worker to search PPG Management. |
| `studentName` | String | `studentName` | Labeled value extracted by CIR and used by the worker to search PPG Management. |
| `advisorName` | String | `advisorName` | Labeled value extracted by CIR and used by the worker to search PPG Management. |

`attachments` as an array is not supported by the current DTOs and should not be offered as a produced list until the contract changes.

## Mapping Versus Transformation

Mapping associates an existing compatible datum with a capability parameter. Transformation or extraction produces a new datum from another datum.

For example, `body:String` cannot be mapped directly to `studentId:Long`. In the current implementation, CIR can extract labeled fields from the email text, and `ValidateAdvisorshipRequestWorker` resolves student/professor IDs by calling PPG Management when name or email is available. That resolution is capability behavior, not a generic mapping transformation.
